# Changelog

## Unreleased

- `activate_view_in_revit(name)` opens a uniquely named view outside a transaction and returns `view_id`, `view_name` and `view_type`. A missing or ambiguous name reports candidate views with their IDs. Hosts can discover the method through `get_bridge_capabilities`.

The add-in lists levels, Revit link instances, family types and type categories for a host to choose from, and `get_available_family_types` finds every type of the categories it is asked for. Install over 0.5.0; the configuration format is unchanged; `get_bridge_capabilities` lists the new method in `methods` (`protocol` stays 2, no new feature flag).

- New `list_model_items` (`kind`, optional `category`, `link_id`, `ids`, `q`, `limit`). `kind` `levels`: `{Id, Name, ElevationMm}`, ordered by elevation, the rows `query("levels")` returns. `links`: one row per Revit link instance, `{Id, Name, TypeId, TypeName, Loaded, DocumentTitle, Origin, Rotated}`, with `Origin` `{X, Y, Z}` in millimetres (origin of the instance's total transform, to 0.1 mm), `Rotated` true when that transform is more than a translation, and `DocumentTitle` null for a link that is not loaded. `types`: `{FamilyTypeId, UniqueId, FamilyName, TypeName, Category, BuiltInCategory}`, the `get_available_family_types` row (`Category` is the category's display name) plus `BuiltInCategory`, the `OST_*` name of the category (null when it is not a built-in category or cannot be read); it needs `category` (an `OST_*` name: every element type of that category, the same list as `get_available_family_types`) or `ids`, and answers `bad_params` without either. `type_categories`: `{Category, DisplayName, Count}` for every category that has element types, `Category` being the `BuiltInCategory` name. `link_id` (a link instance id) reads that loaded link's document instead, for every kind but `links`; elevations are then the link's own, not converted to the host. `ids` (at most 200 element ids; not with `type_categories`) keeps only the rows of those elements, for `levels` and `links` in their usual order; for `types` it looks each id up in the order given, in any category (or only in `category` when that is given too); an id that does not exist or is of another class is simply not in `Items`. `q` keeps the rows whose name contains it, ignoring case; `limit` keeps the first rows; both apply after `ids`. The reply is `{Success, Kind, Items, Total, Truncated, Warnings, Error}`, `Total` counting the rows after `q` and before `limit`. A bad request comes back as `Success: false` with `Error.Code` `unknown_kind`, `bad_category`, `bad_params`, `unknown_link`, `link_not_loaded`, `no_document`, `busy`, `timeout` or `failed` and a `Message`, not as a JSON-RPC error; a row that cannot be read is left out with a line in `Warnings`. No transaction, no dialog, not gated by `allowRemoteCodeExecution`; 15 s timeout.
- `get_available_family_types` with `categoryList` returns every element type of those categories: pipe, duct, stair, railing and other types were missing, because only family symbols and wall, floor, roof, ceiling and curtain system types were searched. The types the earlier search returned come first, in the same order; for a category the earlier search covered only in part, the remaining element types of that category are appended after them. An element type whose category cannot be read is left out, where before the whole call failed. Without `categoryList`, or when none of its names is a category, the reply is unchanged.
- Warnings and errors Revit raises when a command commits its changes no longer open Revit's failure dialog. Before, the dialog blocked Revit until someone closed it while the caller timed out (a snippet deleting a room-bounding wall was reported as failed after 60 s, then committed when the dialog was closed), and a commit Revit rolled back was reported as a success. Every command that changes the model now handles them the way `dry_run_code_in_revit` already did: warnings are dismissed without asking and the commit goes on; errors are never resolved automatically and roll the transaction back, so the model keeps nothing. Per command:
  - `send_code_to_revit` and `manage_solidified_tools` `run`: a reply without failures is unchanged byte for byte. A commit with warnings adds `warnings` (`[{message, elementIds}]`, at most 50 entries of at most 20 ids, in the order Revit posted them) and `warningsTruncated`. A commit that did not succeed gives `success: false`, `result: null`, `warnings`, `warningsTruncated`, `errors` and `errorsTruncated`; `errorMessage` starts `执行失败: 提交被 Revit 拒绝: ` followed by the errors when Revit rolled the transaction back (the model is unchanged), or `执行失败: 提交没有完成: ` with the transaction status for any other outcome (the model may have changed). A snippet that throws is answered as before. `get_bridge_capabilities` reports `features.commit_failures: true`, so that a host can take a reply without `warnings` to mean there were none.
  - `dry_run_code_in_revit`: unchanged (its handling is now the shared one), so its `failures` are what the real run would raise.
  - `create_level`, `color_splash`, `operate_element`: a rejected commit is reported in their usual failure shape with the reason (`create_level`: one line for that level in its message, the other levels go on).
  - `create_dimensions`, `create_room`, `create_grid`, `create_line_based_element`, `create_point_based_element`, `create_surface_based_element`, `create_structural_framing_system`, `tag_rooms`, `tag_walls` and `delete_element` still show their own error box on any error, now also on a rejected commit (`create_structural_framing_system` without its guessed troubleshooting hints), so the caller usually times out before their reply arrives. `delete_element`'s error now carries the reason (`删除元素失败: <reason>`; it was `删除元素失败: 删除元素失败`).
  - Dismissed warnings: `create_level`, `create_line_based_element`, `create_point_based_element`, `create_surface_based_element` and `create_structural_framing_system` list them in their message (`Revit 警告: <text> (元素 <ids>)`). `create_dimensions`, `create_room`, `create_grid`, `tag_rooms`, `tag_walls`, `color_splash`, `delete_element` and `operate_element` have no place for them and do not report them.
  - `create_dimensions`, `create_room`, `create_line_based_element`, `create_point_based_element` and `create_surface_based_element` commit one transaction per item: the items committed before a rejected one stay in the model while the reply is a failure.

One ribbon button, **Revit Bridge**, switches the bridge without any dialog and shows its state; the **Settings** button is gone and its pages are in the new Revit Bridge panel. **Allow my tools** decides whether your own command sets and solidified tools plug in. Install over 0.5.0: the configuration only gains optional keys, and without them a local install behaves as before.

- **Revit MCP Switch** is renamed **Revit Bridge** and is the only button: same id `ID_EXCMD_TOGGLE_REVIT_MCP`, same **Revit MCP Plugin** panel and command class, so UI Automation ids and journals still find it. It says **On** or **Off** (the plug turns green while on), and its tooltip gives the mode, the port or server, **Allow my tools** and the last failure. The "TCP Server Started (port N)", "TCP Server Closed", "WebSocket connection started" and "WebSocket Disconnected" dialogs are gone, so an automated session that invokes the button is no longer stopped by a dialog. A failed start (port in use, access denied, a `commandRegistry.json` that exists but cannot be read, a `token` that is not text) opens the Revit Bridge panel once, non-modal, with the reason. The remote-mode prompts (no server, not paired, revoked) stay dialogs. A second click within 0.8 s of the end of a switch is ignored. The button works with no document open. While the bridge is on, a click always turns it off.
- The **Settings** button (`ID_EXCMD_MCP_SETTINGS`, class `revit_mcp_plugin.Core.Settings`) and its window are removed. Shift+click **Revit Bridge** opens the **Revit Bridge** panel: switch and live status, **Allow my tools**, **Turn the bridge on when Revit starts**, **Connection** (local or remote, pairing, and under **Advanced** the port and "Ask before each ad-hoc code run") and **Advanced: commands**. It opens by itself once per install, on the first switch-on (`panelShown`), and on a failed start.
- New `settings.localTools`, **Allow my tools**: not set, it follows the mode (on in local mode, off in remote mode); an explicit `true` or `false` always wins, and a value that cannot be read counts as off. While it is off, command sets other than the installed `RevitMCPCommandSet` (decided by the DLL's path, not by name) are not loaded, and a request for one of their methods, or for `manage_solidified_tools` `register` or `run`, answers JSON-RPC error `-32002` with a message naming the switch, in local and remote mode; `list` and `delete` still work, and a method whose DLL is missing still answers `-32601`. Unticking takes effect at once; loaded tools stay in memory until Revit restarts and are reused when it is ticked again (a user command is created once per Revit session). A running bridge rebuilds its command list when the box changes, keeping the official command instances, unless `token`, `mode`, `port` or `allowRemoteCodeExecution` in the file changed since it was turned on (or the file cannot be read): then it keeps what it had and asks for a restart of the bridge. Commands are given a read-only view of the running registry, so `get_bridge_capabilities` is right after a rebuild and a command cannot register names of its own.
- `get_bridge_capabilities` adds `"user_tools": {"allowed": ..., "methods": [...]}`, the user commands loaded; the other fields are unchanged (`methods` still lists the installed command set only).
- A command set entry with the name of an installed official method is now skipped; before, the entry listed last replaced the official command.
- New `settings.autoStart`, **Turn the bridge on when Revit starts** (default off); skipped while Revit replays a journal.
- Settings are read key by key: a number or boolean where text is expected is that text (`"token": 12345` is the secret `12345`), numbers in plain decimal notation (`1e2` is `100.0`), `"port": "18090"` is a port, `"true"`/`"false"`/`1`/`0` are booleans; `NaN`, `Infinity` and numbers too large for a decimal affect only their own setting. A value that cannot be read is left at its default instead of discarding the whole file, and the panel and tooltip list it. A `token` that is not text, or a `commandRegistry.json` that exists but cannot be read, keeps the bridge from turning on (before, a damaged file started it with no commands and no token). Saving writes the settings you set and those that changed; any other value, including one the add-in could not read, stays in the file as it was, and the `settings` object written is the one the add-in reads (the last one, in any case).
- The installer keeps `localTools`, `autoStart` and `panelShown` over an update when the previous install had them, reads them, `confirmEachRun` and `allowRemoteCodeExecution` the way the add-in does (`"false"` used to count as true; a value that is not clearly true now leaves remote code execution off), prints whether **Allow my tools** is set, and points to the Revit Bridge panel instead of the Settings pages.

## 0.5.0 (2026-11-17)

The add-in runs a snippet as a dry run that is always rolled back, compiles optional complete C# source files together with a snippet, and tests a built add-in command in the open model without installing it. Install over 0.4.0; the configuration format is unchanged and the existing commands answer as before: `check_code_in_revit` differs only when the new optional `sources` is sent, and `get_bridge_capabilities` only adds feature flags (`protocol` stays 2).

- New `dry_run_code_in_revit` (`code`, optional `parameters`, as for `send_code_to_revit`): runs a snippet and always rolls it back. It compiles through the same step as `send_code_to_revit` (a failed compile opens no transaction and returns `diagnostics`), runs the code in one transaction inside a transaction group, commits that transaction so that Revit reports what was added, modified and deleted and raises its warnings and errors, and then rolls the group back on every path, so the model keeps nothing and the undo list gets no entry. It never shows the confirmation dialog. Warnings are recorded and dismissed, errors are recorded and roll the transaction back without a dialog. The reply is `success`, `rolled_back`, `result`, `error`, `diagnostics`, `changes` (`added` / `modified` with `count`, `by_category` and the first 50 `ids`; `deleted` with `count` and `ids`; `note`), `failures` (`severity`, `text`, `element_ids`) and `fingerprint`. Same 60 s timeout as `send_code_to_revit`; a second dry run is refused while one that timed out is still running, and one Revit has not started in time is withdrawn.
- `dry_run_code_in_revit` and `check_code_in_revit` take an optional `sources`, an array of `{"name", "text"}` complete C# files compiled in the same compilation as the snippet (not wrapped: each file brings its own `using` lines), so a core-logic file can be dry-run as it is and compiled into an add-in unchanged. The symbol blacklist covers the files; their diagnostics add `file` and the line and column in that file (a snippet diagnostic has `file: ""` when files were sent, and no `file` key when none were). At most 20 files and 400 KB of UTF-8 text; over that the request is refused before compiling. The `fingerprint` covers the files in the order given. Without `sources` both methods answer exactly as before.
- `get_bridge_capabilities` reports `features.dry_run`, `features.dry_run_sources` and `features.check_code_sources` (true when the method is registered); `protocol` stays 2.
- In remote mode `dry_run_code_in_revit` needs `allowRemoteCodeExecution`, like `send_code_to_revit`; local mode is unchanged.
- New `test_addin_command_in_revit`: runs a built add-in command in the open model without installing it (DLL copied to a fresh folder and loaded from there, picks clicked on elements given by id, `<name>.input.json`, read-back snippet), reports what it changed and every warning or error, and restores the model by rolling back a transaction group or by Undo (`restore`). New `zoom_view_in_revit` and `capture_view_in_revit`. `features.addin_test`. The manifest gets a second entry, `Type="Command"`, the test loader; the installer reads the add-in's identity from the `Type="Application"` entry. In remote mode `test_addin_command_in_revit` and `capture_view_in_revit` need `allowRemoteCodeExecution`.
- Add-in test timeouts cancel an identified new owned dialog through a bounded native window command and wait for command completion and restoration. No dialog screenshot or simulated input fallback is used. First and repeated element picks are guarded against dialogs and command completion; native foreground activation retries within the request deadline. Ambiguous windows remain untouched and failed cancellation reports unconfirmed restoration.
- Revit can silently drop the posted test loader in transient input states (a key held down, ribbon key tips); the add-in test now posts it again after each 4 s without a start, at most 4 posts within the same 20 s, and `load_error` says how often it was posted and what the last re-post found. A loader invocation that arrives before the next test is set up does nothing.
- An add-in test no longer clicks outside Revit: with Revit minimized it is refused before anything is loaded, and a pick is clicked only when the cursor really reached the point and the window under it is Revit's (its main window or a window it owns); a pick refused that way is retried until the timeout, and the timeout's `error` names it.
- `send_code_to_revit`, its confirmation dialog and its reply are unchanged.

## 0.4.0 (2026-11-10)

The add-in is released for Revit 2020, 2021 and 2023-2026 instead of 2026 only, and the installer installs it for several Revit years at once. Each Revit year is its own install with its own settings, port and pairing. Install over 0.3.1; the configuration format, the commands and the wire formats are unchanged.

- Revit years: 2020 (.NET Framework 4.8, built but not load-tested), 2021, 2023 and 2024 (.NET Framework 4.8), 2025 and 2026 (.NET 8; the 2026 package also runs on Revit 2026.5, which uses .NET 10). Revit 2022 is not supported. Revit 2027 is not supported either: its configuration (`Release R27`, .NET 10) builds, but no package is released and the installer refuses it. README, "Supported Revit years", says which years were tested in a real Revit; the installer warns when it installs a year that was not.
- A release has one package per Revit year, `revit-bridge-addin-<tag>-revit<year>.zip`, and one `SHA256SUMS.txt` for all of them.
- The installer's `-RevitVersion` takes one year, several (`-RevitVersion 2024,2026`) or `installed`. Without it, the installer installs or updates every supported Revit it finds in the registry (it used to install for 2026 only); when it finds none it installs for 2026 as before. Running the one-liner again therefore also installs the add-in for an installed Revit year that did not have it yet.
- Every year is installed on its own, with the guarantees 0.3.1 gave one year: the settings and pairing of that year are kept, its previous install is backed up and put back if copying fails or the run is stopped. A Revit of one year that is open skips only that year, and one year that fails does not undo or stop the others. At the end the installer lists each year as installed, skipped or not installed with the reason, and exits with an error when a year was not installed.
- Only the supported Revit years are found as installed: an installed 2022 or 2027, or 2019 and earlier, is named in one line and left out (an open Revit of such a year does not stop the run). A machine with Revit only in such years gets an error naming them and the supported years; the 2026 fallback is only for a machine with no Revit in the registry. `-RevitVersion` with such a year, or `-Source` with an add-in built for one, is refused before anything is installed.
- `-Pair` pairs exactly one Revit year, because each Revit year is a separate device to the server. The command a bridge site hands out (`-Mode remote -Server ... -Pair <code>`, no year) keeps working: with one supported Revit year installed that year is paired, as with 0.3.1; with several, the installer lists them (with what is installed for each) and asks which one to pair, Enter taking the newest, three tries at most. Where it cannot ask (`-NonInteractive`, input from a pipe or file) it stops before anything is downloaded or redeemed and names the `-RevitVersion <year>` to add. Several years given explicitly with `-Pair` stop the same way. The pairing code is never printed.
- The installer prints one line when two local installs (of any year) use the same TCP port; it does not change ports.
- Releases before v0.4.0 have one package, for Revit 2026: `-Tag v0.3.1 -RevitVersion 2026` still installs it, and another year on such a release is refused with a message instead of getting the 2026 build.
- `-Source <add-in folder>` installs for the year that folder was built for and refuses another year (a 2024 build was installed into `Addins\2026` without a word). `-Source <folder>` also accepts a release's downloaded files (the zips and `SHA256SUMS.txt`), verified like a download, for an offline install.
- A refused pairing code is no longer printed in the installer's error message.
- `send_code_to_revit`, `check_code_in_revit` and `manage_solidified_tools` compile on the .NET Framework years too, also on Revit 2021, whose own older copy of System.Runtime.CompilerServices.Unsafe made the compiler fail before the first line was parsed (`TypeInitializationException` for `PerTypeValues`1`). Request and response shapes are the same on every year.
- The **Settings** window no longer closes by itself a few seconds after it opens (seen on Revit 2021): its owner was guessed from the process and could be a ribbon popup, which takes its owned windows with it when it goes. It is now owned by Revit's main window.
- On Revit 2024 and 2025 the commands no longer use `ElementId(Int32)`, which is deprecated there; element ids are unchanged.
- `commandRegistry.json` names the command set's year folder as `{VERSION}` (`RevitMCPCommandSet/{VERSION}/RevitMCPCommandSet.dll`), which the add-in replaces with the year of the Revit it runs in; registries saved from **Settings > Command sets** already looked like this.
- Building needs the .NET 10 SDK (`global.json`: 10.0.403). One `LangVersion` (12) and one set of `REVIT<year>_OR_GREATER` symbols for both projects (`Directory.Build.props`, `Directory.Build.targets`). New configurations `Debug R27` / `Release R27` (built, not released); `R22` is gone.
- CI builds every released year in a matrix (job `build`: plugin, command set, output check, package per year); job `package` writes `SHA256SUMS.txt`, checks the set (`.github/scripts/check-release.ps1`) and uploads it, with a read-only token; on a `v*` tag only, job `publish`, the only one with write access, publishes all packages in one GitHub Release. No job that runs for a pull request gets a write token.

## 0.3.1 (2026-11-09)

Fixes three ways of losing the pairing or the connection settings, makes the installer safe on Chinese Windows and PowerShell 5.1, and hardens the add-in's settings file and connections. Install over 0.3.0; the configuration format, the command set and the wire formats are unchanged. An update switches commands turned off in Settings back on (see below).

- Saving the **Command sets** page in Settings no longer wipes the connection settings and the pairing. The page rewrote `commandRegistry.json` with only its command list, so `mode`, `wsUrl`, `deviceId`, `token`, `port`, `confirmEachRun`, `allowRemoteCodeExecution` and `logLevel` were lost and the add-in came back as local and unpaired; merely opening the page did the same when the file named a command that no longer exists. It now replaces only `commands` and keeps everything else in the file.
- Re-running the installer (the one-liner) over a paired remote install no longer switches it to local mode. Without `-Mode` an update now keeps the previous mode, and also `port` and `logLevel` (they were reset to 18080 / `Info`). Before, the update wrote `mode: tcp` while keeping the device token, which in local mode is the TCP pre-shared secret, so every local call was refused as well. An explicit `-Mode local` over a paired install now drops the device token, keeps `deviceId` and `wsUrl`, switches `allowRemoteCodeExecution` off with it (unless `-AllowRemoteCode` is passed), and says how to pair again; the report prints the mode actually written. `-Mode remote` over a local install no longer carries the local TCP secret into the remote settings as if it were a device token. `-Server ... -Pair ...` re-pairs an existing remote install without `-Mode`; on a fresh or local install `-Pair` asks for `-Mode remote` before the code is used.
- An update installs the package's command list with every command enabled: commands switched off under **Settings > Command sets** are on again (that page removes a switched-off command from the list, which cannot be told apart from a new command). The installer now names the commands that were not in the previous list or were marked `enabled: false`.
- The installer redeems `-Pair` before it touches the existing install. A wrong or expired code used to leave the add-in already replaced and unpaired; now nothing changes. If copying the new files fails, or the run is stopped half way (Ctrl+C), the previous install is moved back and the message says so. A backup name already taken in the same second gets `-2`, `-3`, ...; the current install used to be moved inside the older backup.
- The installer reads `commandRegistry.json`, `SHA256SUMS.txt` and the `.addin` manifest as UTF-8 explicitly. Under Windows PowerShell 5.1 on Chinese Windows (code page 936) it decoded them in the ANSI code page and wrote the registry back with the em dash and the space after it in `manage_solidified_tools`' description turned into "鈥?". The registry is now written as UTF-8 without BOM on both 5.1 and 7 (5.1 used to add one).
- The installer only refuses to run while Revit of the target year is open; another year (e.g. Revit 2024) can stay open. A Revit process whose path cannot be read still blocks, and the message says why.
- A 404 from `-Server` is called a refused pairing code only when the reply's error is `invalid_code`, as in the add-in; any other 404 says the server address is probably wrong. The server's own message is now shown (it was never read on 5.1 or 7), also when the reply has no Content-Length (chunked, as proxies and CDNs send it).
- Run with `irm | iex`, the installer no longer leaves anything in the PowerShell window it was run from: not its variables (the device token among them), not its helper functions, not `$ErrorActionPreference = 'Stop'`, not a TLS-1.2-only protocol setting. It hides the 5.1 progress bar that slowed the download, adds TLS 1.2 on 5.1 without removing newer protocols, and passes the Windows proxy with the logged-on user's credentials.
- A problem in the installer's closing summary (for example another vendor's `.addin` that cannot be read) is a warning; it used to turn a finished install into a failed one.
- Settings writes are serialized within Revit and atomic: written to a temporary file and renamed over `commandRegistry.json`, so a crash or a parallel write from the WebSocket thread can no longer leave an empty or half-written file or lose a change. The **Connection** page saves, pairs and unpairs through the same locked merge: a revoke (close 4003) handled while the page is open is no longer undone by its Save, properties this version does not know are kept, and a pairing whose code was redeemed but could not be saved says that this Revit is not paired.
- An empty or damaged `commandRegistry.json` no longer makes **Revit MCP Switch** fail with a NullReferenceException: the add-in starts with no commands and logs which file could not be read. The file is left as it is: the Settings pages and the WebSocket thread refuse to write over an empty, `null` or damaged file instead of replacing it with defaults.
- A TCP client that resets the connection right after connecting can no longer crash Revit (the stream was taken outside the error handling on a background thread).
- Stopping and quickly restarting the WebSocket connection no longer leaves two reconnect loops running. Stop no longer waits out the 5 s reconnect delay (it still waits up to 2 s for the socket to close and the worker to end), and a close 4003 that reaches the stopped connection no longer switches remote code execution off.
- The log line for a command skipped for an unsupported Revit version no longer throws a FormatException.
- An invalid port on the Connection page is reported and nothing is saved; it used to be ignored while the page said "Settings saved".
- README: `command.json` lists each command's name, description and assembly path (not parameter schemas); `logLevel` is not read yet; updating keeps the mode and pairing but not the command choices; when `-Mode` and `-Pair` are needed.
- CI checks that `command.json`, `commandRegistry.json` and the `CommandName` of every command class in `commandset` list the same commands, and names the ones missing from each (`.github/scripts/check-commands.ps1`, run before the build).
- CI checks after the build that the output tree has `revit-bridge.addin`, `RevitMCPPlugin.dll`, `commandRegistry.json`, the command set's `command.json` and `RevitMCPCommandSet.dll`, and names every missing file instead of failing in the hash step (`.github/scripts/check-build-output.ps1`).
- On a `v*` tag, CI stops before building unless the tag equals the first three parts of `AssemblyVersion` and the topmost released version in this file (`.github/scripts/check-version.ps1`).
- README: the 26 commands include dynamic C# execution (`send_code_to_revit`, `manage_solidified_tools`); it is not an extra on top of them.

## 0.3.0 (2026-10-26)

The add-in compiles a snippet without running it, reports what it can do, and names a run-time exception by its full type. Install over 0.2.0; configuration and pairing are unchanged. revit-bridge 0.4 uses the new methods; 0.3 keeps working with the old ones.

- New `check_code_in_revit` (`code`, optional `parameters`, which is never evaluated): compiles a snippet with the same wrapper, reference whitelist and symbol blacklist as `send_code_to_revit` - one shared compile step, not a copy - but only emits to memory: nothing is loaded or run, no transaction, no ExternalEvent, no dialog, no active document needed. It runs on the socket thread with a 30 s timeout and returns `compiled`, `diagnostics` (`id`, `severity` error/warning/info, 1-based user-code `line`/`column` or `null` with `in_wrapper: true`, English `message`, `symbol` for CS1061/CS0117/CS0246/CS0103/CS1501/CS1503/CS7036), `truncated` (errors first, at most 50 returned), `fingerprint` (`sha256:` over code, `wrapper_version`, the referenced assembly names and versions, and the add-in version), `wrapper_version` (1) and `errorMessage` (compiler exceptions and timeouts only). A blacklisted symbol is an `RB0001` diagnostic, not an exception.
- New `get_bridge_capabilities`: `protocol` 2, `addin_version`, the registered `methods`, `features` (`check_code`, `structured_diagnostics`, `kit: false`), `revit` (`VersionNumber` / `VersionBuild` / `VersionName`, read once when commands load and cached, so the call never touches Revit objects off the API thread), `runtime` (framework description, CLR version) and `kit: null`. Add-ins without it answer `-32601 Method not found`. To list the registered methods, `CommandManager` now prefers a command constructor taking `(UIApplication, ICommandRegistry)`.
- Neither new method carries `confirm` or is gated by `allowRemoteCodeExecution` in remote mode; both are registered in `commandRegistry.json` and `command.json`.
- `send_code_to_revit` compiles through the same step. Compile errors in `errorMessage` now give the user-code line (they were the 0-based line of the wrapped text, 13 too high) and English messages; a failed compile adds `diagnostics` (same shape as above) and every compile adds `fingerprint`, while `success` / `result` / `errorMessage` are unchanged. A failed compile no longer opens and rolls back a transaction, and a missing active document is reported in `errorMessage` instead of failing inside the error handler.
- A snippet that throws while it runs (`send_code_to_revit`, `manage_solidified_tools` `run`) now names the exception by its full type name: `errorMessage` is `执行失败: <FullName>: <Message>`, e.g. `Autodesk.Revit.Exceptions.ArgumentException: ...` where it used to say `ArgumentException: ...`, which cannot be told apart from the unrelated `System.ArgumentException`. The reflective call's `TargetInvocationException` and an `AggregateException` holding one exception are unwrapped to the exception actually thrown (a `Task.Result` failure used to read `AggregateException: One or more errors occurred. (...)`); its inner exceptions follow as ` ---> <FullName>: <Message>`, so a result that cannot be serialized names both the `JsonSerializationException` and the Revit exception behind it. Failures outside the snippet (no active document, `Commit`) used to give the bare message and now carry the type name too. Only the text changes: no field is added or renamed, compile errors, the forbidden-symbol text and `check_code_in_revit` are unchanged. Clients that only display `errorMessage` are unaffected; one that looked for the short name finds it as the last segment of the full one.

## 0.2.0 (2026-09-23)


Pairing replaces the fixed slots and the pre-shared slot token. Existing remote installs must pair again: get a code from the site and re-run the installer with `-Pair`, or enter it under Settings > Connection. Local (TCP) installs are unaffected.

- Pairing replaces slots: `-Mode remote -Server https://<host> -Pair XXXX-XXXX` redeems the code at `/api/v1/bridge/devices/redeem` and stores `deviceId`, `token` and the `wsUrl` the server returns; **`-Slot` and `-Token` are gone**. The Settings window does the same from a pairing-code field. A 0.1.x config still loads and counts as not paired.
- The WebSocket handshake always sends `{"type":"auth","device_id","token"}` to `<wsUrl>/<deviceId>`. Close 4003 (unpaired or revoked) stops reconnecting and shows that state on the ribbon switch and in the Settings window; close 4002 keeps the retry.
- Pairing switches `allowRemoteCodeExecution` on: the installer's `-Pair` and the Settings window both set it (pass `-AllowRemoteCode:$false` to pair without it), and **Unpair** in the Settings window or a close 4003 from the server clears it again. An update without `-Pair` keeps the previous value.
- Ad-hoc code runs the server marks with a `confirm` object show a Yes/No dialog in Revit (default No, body cut at 2000 characters) before running; No answers `-32001 "declined on device"`. Capability packs, probes and reads never prompt. The `confirmEachRun` setting (default on) turns the dialog off.
- The log file is written as UTF-8 with a BOM. The content was already UTF-8, but without the BOM Windows tools (PowerShell 5.1's `Get-Content`, Notepad) read it in the ANSI code page and showed the Chinese half as mojibake, which made the log useless for diagnosing the confirmation dialog. Existing log files are appended to, not rewritten.
- Reproducible CI build: `Directory.Build.props` sets `Deterministic` and, on GitHub Actions only, `ContinuousIntegrationBuild` (source paths mapped to `/_/`); the workflow prints the SHA-256 of both assemblies so runs can be compared. Local builds keep real paths in the PDB.
- `commandset` builds with 0 warnings: `GeometryUtils.FindIntersection` uses `Curve.Intersect(Curve, CurveIntersectResultOption.Detailed)` on Revit 2026 (old overload kept for older configurations), an unused `catch` variable is dropped, and the meaningless `System.Net.Http` reference (net8) is removed.
