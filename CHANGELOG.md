# Changelog

## Unreleased

The add-in is built for Revit 2020, 2021 and 2023-2027 instead of 2026 only, and the installer installs it for several Revit years at once. Each Revit year is its own install with its own settings, port and pairing. Install over 0.3.1; the configuration format, the commands and the wire formats are unchanged.

- Revit years: 2020 (.NET Framework 4.8, built but not load-tested), 2021, 2023 and 2024 (.NET Framework 4.8), 2025 and 2026 (.NET 8; the 2026 package also runs on Revit 2026.5, which uses .NET 10), 2027 (.NET 10, built but not load-tested yet). Revit 2022 is not supported. README, "Supported Revit years", says which years were tested in a real Revit; the installer warns when it installs a year that was not.
- A release has one package per Revit year, `revit-bridge-addin-<tag>-revit<year>.zip`, and one `SHA256SUMS.txt` for all of them.
- The installer's `-RevitVersion` takes one year, several (`-RevitVersion 2024,2026`) or `installed`. Without it, the installer installs or updates every supported Revit it finds in the registry (it used to install for 2026 only); when it finds none it installs for 2026 as before. Running the one-liner again therefore also installs the add-in for an installed Revit year that did not have it yet.
- Every year is installed on its own, with the guarantees 0.3.1 gave one year: the settings and pairing of that year are kept, its previous install is backed up and put back if copying fails or the run is stopped. A Revit of one year that is open skips only that year, and one year that fails does not undo or stop the others. At the end the installer lists each year as installed, skipped or not installed with the reason, and exits with an error when a year was not installed.
- Only the Revit years this add-in is built for are found as installed: an installed 2022, or 2019 and earlier, is named in one line and left out. A machine with Revit only in such years gets an error naming them and the supported years; the 2026 fallback is only for a machine with no Revit in the registry.
- `-Pair` pairs exactly one Revit year, because each Revit year is a separate device to the server. The command a bridge site hands out (`-Mode remote -Server ... -Pair <code>`, no year) keeps working: with one supported Revit year installed that year is paired, as with 0.3.1; with several, the installer lists them (with what is installed for each) and asks which one to pair, Enter taking the newest, three tries at most. Where it cannot ask (`-NonInteractive`, input from a pipe or file) it stops before anything is downloaded or redeemed and names the `-RevitVersion <year>` to add. Several years given explicitly with `-Pair` stop the same way. The pairing code is never printed.
- The installer prints one line when two local installs (of any year) use the same TCP port; it does not change ports.
- Releases before v0.4.0 have one package, for Revit 2026: `-Tag v0.3.1 -RevitVersion 2026` still installs it, and another year on such a release is refused with a message instead of getting the 2026 build.
- `-Source <add-in folder>` installs for the year that folder was built for and refuses another year (a 2024 build was installed into `Addins\2026` without a word). `-Source <folder>` also accepts a release's downloaded files (the zips and `SHA256SUMS.txt`), verified like a download, for an offline install.
- A refused pairing code is no longer printed in the installer's error message.
- `send_code_to_revit`, `check_code_in_revit` and `manage_solidified_tools` compile on the .NET Framework years too, also on Revit 2021, whose own older copy of System.Runtime.CompilerServices.Unsafe made the compiler fail before the first line was parsed (`TypeInitializationException` for `PerTypeValues`1`). Request and response shapes are the same on every year.
- The **Settings** window no longer closes by itself a few seconds after it opens (seen on Revit 2021): its owner was guessed from the process and could be a ribbon popup, which takes its owned windows with it when it goes. It is now owned by Revit's main window.
- On Revit 2024 and 2025 the commands no longer use `ElementId(Int32)`, which is deprecated there; element ids are unchanged.
- `commandRegistry.json` names the command set's year folder as `{VERSION}` (`RevitMCPCommandSet/{VERSION}/RevitMCPCommandSet.dll`), which the add-in replaces with the year of the Revit it runs in; registries saved from **Settings > Command sets** already looked like this.
- Building needs the .NET 10 SDK (`global.json`: 10.0.403). One `LangVersion` (12) and one set of `REVIT<year>_OR_GREATER` symbols for both projects (`Directory.Build.props`, `Directory.Build.targets`). New configurations `Debug R27` / `Release R27`; `R22` is gone.
- CI builds every year in a matrix (job `build`: plugin, command set, output check, package per year); job `package` writes `SHA256SUMS.txt`, checks the set (`.github/scripts/check-release.ps1`) and uploads it, with a read-only token; on a `v*` tag only, job `publish`, the only one with write access, publishes all packages in one GitHub Release. No job that runs for a pull request gets a write token.

## 0.3.1 (2026-11-09)

Fixes three ways of losing the pairing or the connection settings, makes the installer safe on Chinese Windows and PowerShell 5.1, and hardens the add-in's settings file and connections. Install over 0.3.0; the configuration format, the command set and the wire formats are unchanged. An update switches commands turned off in Settings back on (see below).

- Saving the **Command sets** page in Settings no longer wipes the connection settings and the pairing. The page rewrote `commandRegistry.json` with only its command list, so `mode`, `wsUrl`, `deviceId`, `token`, `port`, `confirmEachRun`, `allowRemoteCodeExecution` and `logLevel` were lost and the add-in came back as local and unpaired; merely opening the page did the same when the file named a command that no longer exists. It now replaces only `commands` and keeps everything else in the file.
- Re-running the installer (the one-liner) over a paired remote install no longer switches it to local mode. Without `-Mode` an update now keeps the previous mode, and also `port` and `logLevel` (they were reset to 18080 / `Info`). Before, the update wrote `mode: tcp` while keeping the device token, which in local mode is the TCP pre-shared secret, so every local call was refused as well. An explicit `-Mode local` over a paired install now drops the device token, keeps `deviceId` and `wsUrl`, switches `allowRemoteCodeExecution` off with it (unless `-AllowRemoteCode` is passed), and says how to pair again; the report prints the mode actually written. `-Mode remote` over a local install no longer carries the local TCP secret into the remote settings as if it were a device token. `-Server ... -Pair ...` re-pairs an existing remote install without `-Mode`; on a fresh or local install `-Pair` asks for `-Mode remote` before the code is used.
- An update installs the package's command list with every command enabled: commands switched off under **Settings > Command sets** are on again (that page removes a switched-off command from the list, which cannot be told apart from a new command). The installer now names the commands that were not in the previous list or were marked `enabled: false`.
- The installer redeems `-Pair` before it touches the existing install. A wrong or expired code used to leave the add-in already replaced and unpaired; now nothing changes. If copying the new files fails, or the run is stopped half way (Ctrl+C), the previous install is moved back and the message says so. A backup name already taken in the same second gets `-2`, `-3`, ...; the current install used to be moved inside the older backup.
- The installer reads `commandRegistry.json`, `SHA256SUMS.txt` and the `.addin` manifest as UTF-8 explicitly. Under Windows PowerShell 5.1 on Chinese Windows (code page 936) it decoded them in the ANSI code page and wrote the registry back with the em dash and the space after it in `manage_solidified_tools`' description turned into "鈥?". The registry is now written as UTF-8 without BOM on both 5.1 and 7 (5.1 used to add one).
- The installer only refuses to run while Revit of the target year is open; another year (e.g. Revit 2024) can stay open. A Revit process whose path cannot be read still blocks, and the message says why.
- A 404 from `-Server` is called a refused pairing code only when the reply's error is `invalid_code`, as in the add-in; any other 404 says the server address is probably wrong. The server's own message is now shown (it was never read on 5.1 or 7), also when the reply has no Content-Length (chunked, as proxies and CDNs send it).
- Run with `irm | iex`, the installer no longer leaves anything in the PowerShell window it was run from: not its variables (the device token among them), not its helper functions, not `$ErrorActionPreference = 'Stop'`, not a TLS-1.2-only protocol setting. It hides the 5.1 progress bar that slowed the download, adds TLS 1.2 on 5.1 without removing newer protocols, and passes the Windows proxy with the logged-on user's credentials.
- A problem in the installer's closing summary (for example another vendor's `.addin` that cannot be read) is a warning; it used to turn a finished install into a failed one.
- Settings writes are serialized within Revit and atomic: written to a temporary file and renamed over `commandRegistry.json`, so a crash or a parallel write from the WebSocket thread can no longer leave an empty or half-written file or lose a change. The **Connection** page saves, pairs and unpairs through the same locked merge: a revoke (close 4003) handled while the page is open is no longer undone by its Save, properties this version does not know are kept, and a pairing whose code was redeemed but could not be saved says that this Revit is not paired.
- An empty or damaged `commandRegistry.json` no longer makes **Revit MCP Switch** fail with a NullReferenceException: the add-in starts with no commands and logs which file could not be read. The file is left as it is: the Settings pages and the WebSocket thread refuse to write over an empty, `null` or damaged file instead of replacing it with defaults.
- A TCP client that resets the connection right after connecting can no longer crash Revit (the stream was taken outside the error handling on a background thread).
- Stopping and quickly restarting the WebSocket connection no longer leaves two reconnect loops running. Stop no longer waits out the 5 s reconnect delay (it still waits up to 2 s for the socket to close and the worker to end), and a close 4003 that reaches the stopped connection no longer switches remote code execution off.
- The log line for a command skipped for an unsupported Revit version no longer throws a FormatException.
- An invalid port on the Connection page is reported and nothing is saved; it used to be ignored while the page said "Settings saved".
- README: `command.json` lists each command's name, description and assembly path (not parameter schemas); `logLevel` is not read yet; updating keeps the mode and pairing but not the command choices; when `-Mode` and `-Pair` are needed.
- CI checks that `command.json`, `commandRegistry.json` and the `CommandName` of every command class in `commandset` list the same commands, and names the ones missing from each (`.github/scripts/check-commands.ps1`, run before the build).
- CI checks after the build that the output tree has `revit-bridge.addin`, `RevitMCPPlugin.dll`, `commandRegistry.json`, the command set's `command.json` and `RevitMCPCommandSet.dll`, and names every missing file instead of failing in the hash step (`.github/scripts/check-build-output.ps1`).
- On a `v*` tag, CI stops before building unless the tag equals the first three parts of `AssemblyVersion` and the topmost released version in this file (`.github/scripts/check-version.ps1`).
- README: the 26 commands include dynamic C# execution (`send_code_to_revit`, `manage_solidified_tools`); it is not an extra on top of them.

## 0.3.0 (2026-10-26)

The add-in compiles a snippet without running it, reports what it can do, and names a run-time exception by its full type. Install over 0.2.0; configuration and pairing are unchanged. revit-bridge 0.4 uses the new methods; 0.3 keeps working with the old ones.

- New `check_code_in_revit` (`code`, optional `parameters`, which is never evaluated): compiles a snippet with the same wrapper, reference whitelist and symbol blacklist as `send_code_to_revit` - one shared compile step, not a copy - but only emits to memory: nothing is loaded or run, no transaction, no ExternalEvent, no dialog, no active document needed. It runs on the socket thread with a 30 s timeout and returns `compiled`, `diagnostics` (`id`, `severity` error/warning/info, 1-based user-code `line`/`column` or `null` with `in_wrapper: true`, English `message`, `symbol` for CS1061/CS0117/CS0246/CS0103/CS1501/CS1503/CS7036), `truncated` (errors first, at most 50 returned), `fingerprint` (`sha256:` over code, `wrapper_version`, the referenced assembly names and versions, and the add-in version), `wrapper_version` (1) and `errorMessage` (compiler exceptions and timeouts only). A blacklisted symbol is an `RB0001` diagnostic, not an exception.
- New `get_bridge_capabilities`: `protocol` 2, `addin_version`, the registered `methods`, `features` (`check_code`, `structured_diagnostics`, `kit: false`), `revit` (`VersionNumber` / `VersionBuild` / `VersionName`, read once when commands load and cached, so the call never touches Revit objects off the API thread), `runtime` (framework description, CLR version) and `kit: null`. Add-ins without it answer `-32601 Method not found`. To list the registered methods, `CommandManager` now prefers a command constructor taking `(UIApplication, ICommandRegistry)`.
- Neither new method carries `confirm` or is gated by `allowRemoteCodeExecution` in remote mode; both are registered in `commandRegistry.json` and `command.json`.
- `send_code_to_revit` compiles through the same step. Compile errors in `errorMessage` now give the user-code line (they were the 0-based line of the wrapped text, 13 too high) and English messages; a failed compile adds `diagnostics` (same shape as above) and every compile adds `fingerprint`, while `success` / `result` / `errorMessage` are unchanged. A failed compile no longer opens and rolls back a transaction, and a missing active document is reported in `errorMessage` instead of failing inside the error handler.
- A snippet that throws while it runs (`send_code_to_revit`, `manage_solidified_tools` `run`) now names the exception by its full type name: `errorMessage` is `执行失败: <FullName>: <Message>`, e.g. `Autodesk.Revit.Exceptions.ArgumentException: ...` where it used to say `ArgumentException: ...`, which cannot be told apart from the unrelated `System.ArgumentException`. The reflective call's `TargetInvocationException` and an `AggregateException` holding one exception are unwrapped to the exception actually thrown (a `Task.Result` failure used to read `AggregateException: One or more errors occurred. (...)`); its inner exceptions follow as ` ---> <FullName>: <Message>`, so a result that cannot be serialized names both the `JsonSerializationException` and the Revit exception behind it. Failures outside the snippet (no active document, `Commit`) used to give the bare message and now carry the type name too. Only the text changes: no field is added or renamed, compile errors, the forbidden-symbol text and `check_code_in_revit` are unchanged. Clients that only display `errorMessage` are unaffected; one that looked for the short name finds it as the last segment of the full one.

## 0.2.0 (2026-09-23)


Pairing replaces the fixed slots and the pre-shared slot token. Existing remote installs must pair again: get a code from the site and re-run the installer with `-Pair`, or enter it under Settings > Connection. Local (TCP) installs are unaffected.

- Pairing replaces slots: `-Mode remote -Server https://<host> -Pair XXXX-XXXX` redeems the code at `/api/v1/bridge/devices/redeem` and stores `deviceId`, `token` and the `wsUrl` the server returns; **`-Slot` and `-Token` are gone**. The Settings window does the same from a pairing-code field. A 0.1.x config still loads and counts as not paired.
- The WebSocket handshake always sends `{"type":"auth","device_id","token"}` to `<wsUrl>/<deviceId>`. Close 4003 (unpaired or revoked) stops reconnecting and shows that state on the ribbon switch and in the Settings window; close 4002 keeps the retry.
- Pairing switches `allowRemoteCodeExecution` on: the installer's `-Pair` and the Settings window both set it (pass `-AllowRemoteCode:$false` to pair without it), and **Unpair** in the Settings window or a close 4003 from the server clears it again. An update without `-Pair` keeps the previous value.
- Ad-hoc code runs the server marks with a `confirm` object show a Yes/No dialog in Revit (default No, body cut at 2000 characters) before running; No answers `-32001 "declined on device"`. Capability packs, probes and reads never prompt. The `confirmEachRun` setting (default on) turns the dialog off.
- The log file is written as UTF-8 with a BOM. The content was already UTF-8, but without the BOM Windows tools (PowerShell 5.1's `Get-Content`, Notepad) read it in the ANSI code page and showed the Chinese half as mojibake, which made the log useless for diagnosing the confirmation dialog. Existing log files are appended to, not rewritten.
- Reproducible CI build: `Directory.Build.props` sets `Deterministic` and, on GitHub Actions only, `ContinuousIntegrationBuild` (source paths mapped to `/_/`); the workflow prints the SHA-256 of both assemblies so runs can be compared. Local builds keep real paths in the PDB.
- `commandset` builds with 0 warnings: `GeometryUtils.FindIntersection` uses `Curve.Intersect(Curve, CurveIntersectResultOption.Detailed)` on Revit 2026 (old overload kept for older configurations), an unused `catch` variable is dropped, and the meaningless `System.Net.Http` reference (net8) is removed.

## 0.1.1 (2026-09-17)

- No built-in WebSocket server URL: `wsUrl` comes only from `commandRegistry.json` (installer `-Server` or the Settings page). The Settings page no longer pre-fills a host; the switch shows a message instead of connecting when `wsUrl` is empty in `websocket` mode.

## 0.1.0 (2026-09-17)

First release under the revitbridge organization. History before this point lives in `imkcrevit/revit-api-rag` (`revit_plugin/`), imported with `git subtree split`.

- New add-in identity: `Name` `revit-bridge`, `VendorId` `RevitBridge`, new `ClientId`; installs into `Addins\2026\revit-bridge\` so it can coexist with upstream `mcp-servers-for-revit`.
- `global.json` pins the .NET SDK (9.0.313, `rollForward: latestFeature`); GitHub Actions builds `Release R26`, packages `revit-bridge-addin-<tag>.zip` + `SHA256SUMS.txt` and publishes them on `v*` tags. Optional Authenticode step, off by default.
- `installer/install.ps1`: one-line install from GitHub Releases with checksum verification, `-Mode local|remote`, `-Source release|<dir>`, no token file required, `-AllowRemoteCode` off by default.
- Build output `plugin\bin\AddIn 2026 Release R26\` is now a complete installable tree (manifest + folder + default `commandRegistry.json`).
- Shipped `commandRegistry.json` defaults to `mode: "tcp"`.
- Added `NOTICE`, `THIRD_PARTY_NOTICES.md`, `FORKING.md`; removed the demo-kit README and `install-revit-demo.ps1`.
